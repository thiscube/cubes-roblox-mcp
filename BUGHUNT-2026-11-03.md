# Bug hunt, 2026-11-03

**Status: findings 1 to 5 are fixed, with tests.** The two window fix needs the plugin reinstalled, and nothing was tried in real Studio. What follows is the audit as written.

A quick audit of the `activity-labels` branch at `f310c36`. The audit itself changed no code. Findings 1 to 4 were run against the built server using a real MCP client and fake Studio windows that post what `Transport.luau` posts. Nothing ran in real Studio.

## 1. An unanswered delete prompt counts as yes: `src/server.ts:405`

**Breaks:** a destructive batch runs without the human agreeing, which is the exact thing the prompt exists to stop.

**Trigger:** the client supports elicitation. The model calls `mutate {ops:[{op:"delete",target:"ServerScriptService"}], confirm:true}`. Nobody answers for 60 seconds.

**Path:** `handleMutate` → `confirmWithUser` → `server.elicitInput` hits the SDK's default 60s request timeout → the `catch` returns `null`, the value that means "this client cannot ask" → `server.ts:842` then accepts the model's own `confirm: true` → `bridge.send("mutate")`.

**Why the guards miss it:** `null` covers both "cannot ask" and "asked and it failed". The comment at `server.ts:825` says the flag only counts when the client cannot elicit. A decline or cancel is handled correctly and returns `false`.

**Confidence:** confirmed. Output: `prompted human: 1 time(s); waited 60s with no answer`, `mutate reached Studio: true`. Not tried inside the Claude app itself.

**Fix:** in the `catch`, return `false`. Only the missing-capability branch at line 388 should return `null`. Consider a longer timeout on `elicitInput`, since 60s is short for a person.

## 2. Two Studio windows look like one, and the backup comes from the wrong window: `plugin/src/Transport.luau:1258`

**Breaks:** a script edit is backed up from one window and written to the other, and the warning about this can never fire.

**Trigger:** two Studio windows open with the plugin, writes on in both, then `mutate` with a `set Source`.

**Path:** the poll body sends only `writeEnabled` and `protocol`, no `instanceId` → `bridge.ts:651` files both windows under `DEFAULT_INSTANCE` → `listInstances()` returns 1, so the `instances.length > 1` note at `tools/session.ts:43` is dead → `captureScriptHistory` (`server.ts:939`) goes to the first parked window and `bridge.send("mutate")` (`server.ts:860`) to the next.

**Also:** the shared entry's write toggle becomes whichever window polled last. With one window off and one on, `writeEnabled` flips on every poll, so calls fail on and off. The plugin's own check at `Transport.luau:518` still stops a write landing in the window that is off.

**Why the guards miss it:** the "every window must be ON" rule at `bridge.ts:519` works per id, and the shipped plugin never sends one. The tests exercise ids the real plugin does not send.

**Confidence:** confirmed with fake windows. Output, three times out of three: `A<-eval  B<-mutate`, `windows the server sees: 1`.

**Fix:** send a per-window id, place id and place name in the poll body. Then let tools address a window and send all of one call's commands to the same window. The bridge already routes by `target`.

## 3. Studio working for over 30 seconds reads as Studio gone: `src/bridge.ts:476`

**Breaks:** other calls fail with "most likely in Play mode", and writes count as off, while the plugin is alive and busy.

**Trigger:** a command running longer than 30s, such as `mesh_bake` with its 90s budget or a slow `run_code`, and any second call during it.

**Path:** the plugin does not poll while dispatching (`Transport.luau:1362`) → `lastSeen` goes stale → `connected` is false after `HEARTBEAT_WINDOW_MS` → `send` rejects with `studio_not_connected`.

**Why the guards miss it:** nothing counts commands in flight as signs of life.

**Confidence:** confirmed, with the clock moved forward 31s rather than a real wait. Output: `connected while the command is running: false`.

**Fix:** treat the plugin as connected while a handed-over command is still pending and within its own timeout.

## 4. A failed `script_edit` is flagged as a success: `src/tools/scripts.ts:226`

**Breaks:** the client's error flag says the call worked when the edit did not apply.

**Trigger:** `script_edit` with no `confirm`, or one whose write Studio rolls back.

**Path:** the tool nests the failure under `result` and returns no top-level `error` → `server.ts:691` looks only at the top level → no `isError`.

**Why the guards miss it:** `macro_run` and `script_restore` were fixed for this last round; `script_edit` was not. The body does say `edited: false`, so a careful reader can still tell.

**Confidence:** confirmed. Output: `edited: false | inner: mutate_failed | isError: false`.

**Fix:** copy the inner `error` to the top level, as `script_restore` does at `scripts.ts:432`.

## 5. The checks can't pass on Windows: `package.json:24`

**Breaks:** `npm run ci`, which `CLAUDE.md` says to run before pushing, stops at once on Windows. Run by hand, 5 of 431 tests fail.

**Trigger:** `npm run ci` on this machine. `CUBES_MCP_OFFLINE=1 node ...` is not valid in cmd.

**The 5 failures:** `test/unit/assets.test.mjs:262`, `:281`, `:486` and `test/unit/bridge.test.mjs:725`, `:732`. Two need symlink rights, one assumes `/` is the root, two assume POSIX file modes. All five are test assumptions rather than product bugs.

**Confidence:** confirmed.

**Fix:** have `test/run.mjs` set the variable itself when asked, and skip the five on Windows.

## Not a bug, but worth changing

- **Read tools stop working with writes off.** All 41 `eval` tools are refused, including `script_read`, `find_references`, `logs_tail`, `debug_error`, `tags_find` and `perf_stats`. This fails safe and was deliberate in `f310c36`, but it makes the off switch much less useful. The comment at `scripts.ts:172` still says this read is safe with writes off.
- **Generated Luau is never compiled in tests.** That is how `script_edit` shipped sending literal `${luaJson(...)}` text last round. A syntax check over the templates would have caught it, and it is the part of `A1` still open. It needs a Luau parser, so it is a dependency decision.
